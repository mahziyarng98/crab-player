# Packaging

Crab Player ships in six forms so that every major distribution family has
a way in. This page says what each one is, how it is built, and what was
actually tested. The status table at the end is the honest summary.

## Application id

One reverse-DNS id is used everywhere: **`io.github.mahziyarng98.CrabPlayer`**.

| Where | Value |
| --- | --- |
| Wayland `app_id`, X11 `WM_CLASS` | `io.github.mahziyarng98.CrabPlayer` (`app::APP_ID`) |
| Desktop file | `io.github.mahziyarng98.CrabPlayer.desktop`, `StartupWMClass` and `Icon` the same |
| Icons | `hicolor/<size>/apps/io.github.mahziyarng98.CrabPlayer.png` |
| AppStream | `io.github.mahziyarng98.CrabPlayer.metainfo.xml`, `<id>` the same |
| Flatpak | `app-id: io.github.mahziyarng98.CrabPlayer` |
| Binary, config, data | stay `crab-player` (`~/.config/crab-player`, `~/.local/share/crab-player`) |

Why: Flatpak and Flathub require the desktop file, the icon and the
AppStream id to be the reverse-DNS app id, and compositors find a window's
icon through the desktop file whose name matches the window's app id. The
earlier setup used `crab-player` for the window but
`io.github.crabplayer.CrabPlayer` for the Flatpak, so one of the two would
always have shown a generic icon. `io.github.<user>.<App>` is the form
Flathub accepts for projects hosted on GitHub without a domain of their
own. A unit test (`app_id_matches_the_packaging`) fails if the desktop
file, the AppStream file or the Flatpak manifest drift from `APP_ID`.

Checked on the real Hyprland session: the window's class is the new id,
and GIO resolves it to the installed desktop entry and its 48 px icon.
Omarchy's bar has no per-window icons, so no taskbar picture is shown.

The old `crab-player.desktop` and `crab-player.png` icons from an earlier
user install are removed by `scripts/install.sh` (it uninstalls the
previous manifest first). Default-application settings are never touched.

## libmpv is loaded at runtime

`libmpv2-sys` links `-lmpv`, which made `libmpv.so.2` a hard dependency: on
a system without it the dynamic loader refused to start the program, with
a message most desktop users never see. Now `src/player/mpv_shim.rs`
(generated by `scripts/gen-mpv-shim.py`) defines every `mpv_*` function in
the binary as a forwarder resolved with `dlsym`; the linker satisfies all
references locally and `--as-needed` drops `libmpv.so.2` from `DT_NEEDED`
(CI checks this with `readelf`). `player::mpv_dl` opens the library at
startup and requires client API 2 (mpv 0.35+).

If libmpv is missing or too old, the player still starts: stderr names the
package to install for each distribution family, the window shows the same
advice in its error banner, and playback falls back to the null backend.
`CRAB_PLAYER_LIBMPV=/path/to/libmpv.so.2` overrides which library is
opened.

The binary's only `DT_NEEDED` entries are now glibc and `libgcc_s`;
OpenGL, EGL, Wayland and X11 were already opened at runtime by winit and
glutin. That is why the packages list those libraries by hand.

## Formats

### AppImage (any distribution)

`packaging/appimage/build.sh` → `dist/Crab_Player-<version>-x86_64.AppImage`
and the generic tarball.

- Built in an `ubuntu:22.04` container (docker or podman), so it needs
  glibc 2.35 or newer: Ubuntu 22.04+, Debian 12+, Fedora 36+, openSUSE
  Tumbleweed and Leap 16, RHEL 10, Arch.
- Bundles libmpv 0.36.0, built in the container with only the library
  (no command line player, no Lua or JavaScript), and its media stack from
  Ubuntu 22.04: FFmpeg 4.4 and its codec libraries, libass, libpulse.
- Never bundles glibc, libstdc++ or the GPU stack (libGL/libEGL/libGLX/
  libgbm/libdrm/libvulkan): they always come from the host, so they match
  its drivers.
- libva, libvdpau, ALSA, D-Bus, udev, fontconfig/freetype/harfbuzz, expat,
  zlib, libuuid and the X11/xcb/Wayland/xkbcommon client libraries are
  per-library fallbacks: each sits in its own directory, and `AppRun` adds
  a directory to `LD_LIBRARY_PATH` only when the host has no library of
  that name. On a normal desktop none is used (no `LD_LIBRARY_PATH` at
  all), so VA-API runs on the host's libva and drivers, ALSA on its
  plugins and fonts on its configuration; a minimal system still gets a
  working player.
- Everything else libmpv needs is bundled, including libraries whose
  presence differs between distributions (`libpcre.so.3` and libselinux
  are missing on Arch, for example).
- Libraries find each other through `RUNPATH=$ORIGIN`, not
  `LD_LIBRARY_PATH`, so programs the player starts (a browser for a link)
  do not inherit the bundle.
- Packed with appimagetool 1.9.1 and the type2 runtime 20251108, both
  pinned and checked by sha256.
- Uses the static AppImage runtime (no libfuse2 needed). Without FUSE (in
  a container) run it with `--appimage-extract-and-run`.

### Debian and Ubuntu (.deb)

`packaging/debian/build.sh` → `dist/crab-player_<version>-1_amd64.deb`.

- debhelper packaging in `packaging/debian/`, built with
  `dpkg-buildpackage` in a `debian:bookworm` container. Rust 1.95+ is newer
  than any Debian or Ubuntu LTS ships, so cargo comes from rustup and is
  not a `Build-Depends`.
- Depends on `libmpv2 (>= 0.35)`: Debian 12 and 13, Ubuntu 23.04 and newer.
  Ubuntu 22.04 only has `libmpv1` (client API 1), which this player cannot
  use; use the AppImage or the Flatpak there.
- The `ffmpeg` command line tool is no longer a dependency: `libmpv2`
  pulls in the FFmpeg libraries. Recommends `libavcodec-extra`, the
  portals and a VA-API driver.

### Fedora, RHEL-compatible, openSUSE (.rpm)

`packaging/rpm/build.sh` → `dist/crab-player-<version>-1.fc45.x86_64.rpm`
from `packaging/rpm/crab-player.spec`.

- Built in a `fedora:45` container (`RPM_IMAGE` picks another one).
- Requirements are sonames (`libmpv.so.2()(64bit)`, `libEGL.so.1()(64bit)`,
  …), so the same package resolves to `mpv-libs` on Fedora and `libmpv2`
  on openSUSE.
- Fedora's own FFmpeg (`ffmpeg-free`) leaves out patented codecs such as
  H.264 and HEVC; install `ffmpeg-libs` from RPM Fusion (`sudo dnf swap
  ffmpeg-free ffmpeg --allowerasing`). On openSUSE the Packman repository
  provides the full codec set.
- A package built on Fedora 45 needs Fedora 45's glibc or newer. RHEL 9
  and openSUSE Leap 15 are older: use the AppImage or the Flatpak there.

### Arch Linux

`packaging/arch/build-local.sh` builds `PKGBUILD` from the checkout into
`target/arch/` without installing anything. `PKGBUILD-git` builds the
development version from the `main` branch.

For the AUR (nothing has been published):

1. Tag the release and let the release workflow publish it.
2. Copy `packaging/arch/PKGBUILD` into a clone of
   `ssh://aur@aur.archlinux.org/crab-player.git`, run `updpkgsums` (fills
   in the tarball checksum) and `makepkg --printsrcinfo > .SRCINFO`.
3. Build it once with `makepkg -si` in a clean chroot
   (`extra-x86_64-build` from `devtools`), then commit and push.
4. For `crab-player-git`, do the same with `PKGBUILD-git` (its `pkgver()`
   follows the tags).

### Flatpak

`packaging/flatpak/build.sh` → a local repository and
`dist/Crab_Player-<version>-x86_64.flatpak`; `--install` also installs it
for the current user.

- `org.freedesktop.Platform` 26.08: FFmpeg, libva and Mesa's VA-API
  drivers come from the runtime; the `codecs-extra` extension adds the
  patented codecs and is installed automatically from Flathub.
- libass 0.17.4, libplacebo 7.360.1 and libmpv 0.41.0 are built as
  modules: libass and mpv from release tarballs checked by sha256,
  libplacebo from git pinned to its tag's commit (its submodules are part
  of the build).
- Sandbox: Wayland with X11 fallback, DRI (GPU and VA-API), PulseAudio,
  network for streams. Files come through the file chooser portal and,
  for "Open with", the document portal; drag and drop from a file manager
  passes plain paths, so `~/Videos`, `~/Music` and `~/Downloads` are
  readable. Saved images go to `~/Pictures/crab-player`.
- `packaging/flatpak/cargo-sources.py` turns `Cargo.lock` into
  `cargo-sources.json` (every crate as a checksummed source), because
  flatpak-builder builds offline.
- For Flathub the `dir` source of the crab-player module becomes a `git`
  source pinned to the release tag.

#### Submitting to Flathub (not done yet)

1. Fork `flathub/flathub` and branch off `new-pr`.
2. Copy `packaging/flatpak/io.github.mahziyarng98.CrabPlayer.yml` and
   `cargo-sources.json` into
   `io.github.mahziyarng98.CrabPlayer/`, and replace the crab-player
   module's `dir` source with a `git` source at the `v0.1.0` tag:
   `url: https://github.com/mahziyarng98/crab-player.git`, `tag: v0.1.0`,
   `commit: <the tagged commit>`.
3. Regenerate `cargo-sources.json` from that tag's `Cargo.lock` with
   `packaging/flatpak/cargo-sources.py`, and build the bundle locally with
   `flatpak-builder --repo=repo --force-clean build-dir <manifest>` to
   confirm it still starts and plays.
4. Open the pull request; the reviewers check the licence, the AppStream
   metadata (`appstreamcli validate` passes) and that no network access is
   requested beyond the `finish-args` in the manifest. Flathub's CI then
   builds it and publishes after the merge.
5. Later versions are a pull request in that repository that bumps the tag
   and `cargo-sources.json`; nothing is published from this repository.

### Generic tarball and install script

`packaging/tarball.sh` (called by the AppImage build) →
`dist/crab-player-<version>-linux-x86_64.tar.gz`: the binary built on the
glibc 2.35 baseline, the desktop entry, AppStream file, icons and
`scripts/install.sh` / `uninstall.sh`. It needs `libmpv.so.2` from the
system.

```sh
scripts/install.sh                              # ~/.local, no root
sudo scripts/install.sh --prefix /usr/local     # system-wide (from a checkout: build first, add --no-build)
DESTDIR=/tmp/stage scripts/install.sh --prefix /usr/local --no-build   # staged, no root
scripts/uninstall.sh [--prefix /usr/local]
```

`install.sh` refuses to write outside `$HOME` without root (unless
`DESTDIR` stages it), refuses to run cargo as root, writes a manifest of
what it installed, and `uninstall.sh` removes exactly that.

## Release workflow

`.github/workflows/release.yml` runs on a `v*` tag: AppImage and tarball
(in `ubuntu:22.04`), `.deb` (`debian:bookworm`), `.rpm` (`fedora:45`), the
Arch package (`archlinux:base-devel`) and the Flatpak bundle (best effort:
it does not block the release). The last job writes `SHA256SUMS` and
creates the GitHub release with `gh release create`, using only the
built-in `GITHUB_TOKEN` with `contents: write` for that job; every other
job has `contents: read`. Actions are pinned to commit SHAs. The release
body comes from `docs/release-notes/<tag>.md` when that file exists.

A manual run (`workflow_dispatch`) builds the same packages as artifacts
and publishes nothing, so a release can be rehearsed without tagging:

```sh
gh workflow run release.yml --ref main
```

The AppImage build pins appimagetool 1.9.1 and the type2 runtime 20251108
to their release URLs and verifies both SHA-256 checksums before use.

On GitHub-hosted runners, `azure.archive.ubuntu.com` and
`archive.ubuntu.com` do not resolve, so the jobs install packages through
`.github/actions/apt-install`, which tries several Ubuntu mirrors with
bounded timeouts (and the `ubuntu:22.04` container job repoints its
`sources.list` the same way).

`.github/workflows/ci.yml` runs on every push and pull request: rustfmt,
clippy (`-D warnings`) and tests with and without the `mpv` feature, the
libmpv-not-linked check, desktop-file and AppStream validation, and
shellcheck.

## Testing a package

`packaging/test-in-container.sh <image> <artifact>` installs a `.deb`,
`.rpm` or `.AppImage` in a clean container with only Xvfb and Mesa added,
plays a generated H.264/AAC clip and lists which libmpv, FFmpeg and GL
libraries the process mapped.
